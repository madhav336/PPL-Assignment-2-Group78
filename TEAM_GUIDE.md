## 2. The golden rules (never break these)

1. **Only touch the files for your own problem.** Never edit another person's
   code, tests or prompt log, not even to "fix a typo".
2. **S1 is frozen.** Don't edit `78/code/78_q3.rkt`, `78/tests/test_q3.rkt` or
   `78/prompts/S1.md`.
3. **One unit per prompt, one unit per commit.** A unit is one function or
   predicate (with its private helpers), one test file, one review, or one fix.
4. **Every prompt that produces, reviews or fixes solution work is logged word
   for word** in your problem's prompt file.
5. **The AI never commits or pushes.** It writes code and gives you the
   commands; you run them yourself, from your own account.
6. **No AI attribution anywhere:** no `Co-Authored-By: Claude` or ChatGPT lines,
   and no "generated by AI" text in commits, code or files.
7. **No unnecessary edits:** no reformatting, renaming, reordering, or "cleanup"
   of anything your unit doesn't need.
8. **Existing work must keep working.** Rerun all tests for your problem before
   every commit.
9. **Keep it inside the group.** The repo is private. Sharing code, prompts or
   skill files with another group is an integrity violation.
10. **Understand everything you commit.** There is a 4-mark individual viva on
    ownership. If you can't explain a line, don't commit it.

## 4. The unit workflow (do this every time)

1. **Pull first:** `git pull`. Never start on a stale copy.
2. **Check what's done:** `git log --oneline` and your prompt log.
3. **Pick the next unit** from the plan (Section 10). Exactly one.
4. **Write the prompt** (Section 5). Drafting it with ChatGPT is fine, but read it
   and make sure it asks for one unit only.
5. **Send the prompt to the coding AI** (Claude Code in this repo, or another AI
   with `CLAUDE.md` and the skill file pasted in first).
6. **Read the AI's answer properly.** Check:
   - it did only the unit you asked for;
   - it showed the exact diff, and the diff touches only your file(s);
   - it ran the tests and showed expected vs actual output;
   - the whitelist / library check is clean;
   - loading the file prints nothing.
7. **Log the prompt** (Section 6). The S1 habit: the unit prompt says "do not
   modify prompt logs", and afterwards you ask the AI to "log Prompt N" in a
   separate message. Logging it yourself is also fine.
8. **Verify yourself** before committing (Section 8). Don't rely only on the
   AI's report.
9. **Check exactly what changed:**
   ```
   git status
   git diff
   ```
   Only your unit's file(s) and your prompt log should appear. If anything else
   shows up, **stop** and find out why before committing.
10. **Commit and push** (Section 7).
11. **Never end a session with uncommitted work.** `git status` must be clean
    before you stop.

## 5. Writing prompts

### Every prompt must
- **Name the skill:** start with "Using the scheme-dev skill." or "Using the
  prolog-dev skill."
- **Name the unit and its ID:** `Unit: S2.b1 — my-length only.`
- **Name the file** and say what may change and what must not ("Do not alter
  existing functions").
- **Quote the spec** the unit must meet (from the handout).
- **List the constraints** that matter (whitelist, banned libraries, output format).
- **Ask for explanations** (declarative or recursive reading, tail calls, edge
  cases); you will need them for the viva.
- **Ask for verification:** exact tests, expected vs actual output, whitelist
  check, silent-on-load check, and the exact diff.
- **Set restrictions:** "Do not implement any other unit. Do not modify prompt
  logs or unrelated files. Do not commit or push."

### Never send
- Whole-problem prompts: "Do S2", "Solve P1", "Finish the rest", "Continue".
- Vague one-liners for real work. S1's first prompt, "S1 tree traversals", was
  too vague. The AI only did S1.a because of the rules, and the review and fix
  prompts were needed afterwards. Learn from it.
- Prompts that ask the AI to commit, push, change git config, or edit other
  people's files.

### Template (copy, fill in, keep the structure)
```
Using the <scheme-dev | prolog-dev> skill. Read and follow the complete skill file.
Unit: <ID> — <what, in one line>.
File: 78/code/78_qN.<rkt|pl>.
Scope: <exactly what to add>. Do not alter <existing functions/units>.
Assignment specification:
* <rule 1 from the handout>
* <rule 2 ...>
Constraints:
* <whitelist / allowed libraries / output format>
* The file must contain definitions only and loading it must print nothing.
Explain:
1. <base case / declarative reading>
2. <tail-call behaviour / edge cases>
Verification:
* <test 1 with expected result>
* <test 2 ...>
Show the exact tests and outputs and the exact diff.
Restrictions: Do not implement any other unit. Do not modify prompt logs or unrelated files. Do not commit or push.
```

### Prompts drafted with ChatGPT (or any other AI)
- **Allowed:** the handout permits any generative AI tool. All of Madhav's S1

- **Log exactly what you sent** to the coding AI, not the ChatGPT conversation

- **Be open about it:** add `drafted with: ChatGPT` to the log header (Section 6).
- **Read every drafted prompt before sending it.** If ChatGPT wrote a
  whole-problem prompt, cut it down to one unit.

## 6. Prompt log rules (`78/prompts/<P1|P2|S2>.md`)

### Exact format (copy from `78/prompts/S1.md`)
`````markdown
## Prompt N (unit: <ID> — <short description>, sent by: <your name>, drafted with: <ChatGPT | self>)

````
<the exact prompt text you sent, unedited>
````

> Note (group): <what happened: result, test counts, anything unusual>
`````

### Small rules
- **Number prompts 1, 2, 3, ...** separately in each file, in the order you sent
  them. No gaps, no reordering.
- **Word for word:** keep typos, odd spacing, bullet characters and dashes exactly
  as sent.
- **Use a four-backtick fence** (````) around the prompt so that backticks inside
  it don't break the markdown.
- **Never edit a prompt after it was sent.** Any explanation or correction goes
  in a `> Note (group):` line under it.
- **If the prompt had no header line,** add one when logging and say so in the
  note ("header added when logging").
- **If the log entry was added after the unit** (the usual S1 habit), say so in
  the note ("this entry was added afterwards in a separate request").
- **Follow-up, fix and review prompts are logged too**, each as its own numbered
  entry with its own unit ID (`S2.b review`, `S2.b fix`).
- **Housekeeping messages are not logged:** "log Prompt N", "give me the commit
  commands", "yes". This is the group's convention. If a message changed
  solution code or tests, it **must** be logged.
- **Append only.** Never delete or rewrite older entries, yours or anyone else's.
- **Commit the log entry together with the unit it belongs to.**

## 7. Commit rules

- **One unit = one commit**, containing that unit's code or test change **plus**
  its prompt log entry. A review with no code change is a commit of just the
  log entry.
- **Message format:** `<unit>: <what changed>`, in the imperative, short, with
  no AI attribution. Real examples from S1:
  - `S1.a: add inorder traversal and print-inorder`
  - `S1.a review: log review prompt and verdict`
  - `S1.a fix: note non-recursive functions in comments`
  - `S1.b: add preorder, postorder and print-all-traversals`
  - `S1 tests: add test_q3.rkt with PDF examples and edge cases`
  - `S1 final review: log review prompt and verdict`
- **Stage files by name.** Never `git add .` or `git add -A`:
  ```
  git add 78/code/78_q4.rkt 78/prompts/S2.md
  git commit -m "S2.b1: add my-length"
  git push
  ```
- **Before committing,** run `git diff --staged` to see exactly what is going in.
- **Push right after each commit,** so teammates see your progress and nothing is lost.
- **Never** `git commit --amend` a pushed commit, `git push --force`,
  `git rebase` on `main`, or `git reset --hard` without the group agreeing.
  Keep history linear and honest.
- **Never commit broken code.** Test first.
- **Never bundle units.** Two functions in one commit hides the section-by-section
  history, which is graded (2 marks individual, 2 marks group process).
- **If `git pull` gives a conflict, stop.** Don't resolve it by deleting someone
  else's work. Ask the group.
- **If an AI tool adds `Co-Authored-By` or similar to a commit message,** remove
  it before committing.

## 8. Code and test rules

### Every code file
- **Definitions only.** Loading the file must print **nothing**. No test calls,
  no debug `display` / `print`, nothing at the top level except definitions
  (and `use_module` in Prolog).
- **Racket:** line 1 is exactly `#lang racket/base` (not `#lang racket`). No
  `provide` or `require`. **Only the whitelisted built-ins** (see `CLAUDE.md`
  and `scheme-dev/SKILL.md`). Replace banned functions with `my-` helpers.
- **Prolog:** no `:- initialization`, no `halt`, no `assert`, `retract`,
  `b_setval` or `nb_setval`. Libraries: **only** `lists`, `apply`, `yall`,
  `aggregate` (no `clpfd`). No singleton or discontiguous warnings on load.
- **Never hard-code answers** (P1's solution, P2's equations, expected outputs).
- **Every function or predicate gets a comment:** its contract, its recursive or
  declarative reading, and whether it is tail recursive ("Not recursive." where
  true). Follow the S1 style in `78_q3.rkt`.
- **Naming:** Scheme `kebab-case`, `?` for predicates, `my-` for replacement
  helpers. Prolog `snake_case` predicates, `CamelCase` variables.
- **New code goes below existing code,** under a section header comment like
  `;; S2.b: ...` (Scheme) or `% P1.b: ...` (Prolog).
- **Don't change existing lines.** If a fix is really needed, it is its own
  "fix" unit with its own prompt and commit.
- **Keep the formatting:** spaces, not tabs; keep the existing indentation style;
  don't reflow comments.
- **Line endings:** if `git diff` shows **every line** of a file as changed, your
  editor changed the line endings. Stop and undo it; don't commit that.

### Tests
- **One test file per problem:** `78/tests/test_q1.pl`, `test_q2.pl`, `test_q4.rkt`.
- **Racket test files:** calls only, no `#lang`, with each expected output line
  in a `; expect: ` comment above the call. Copy the layout of `test_q3.rkt`.
- **Prolog test files:** plunit, starting with `:- consult('../code/78_q1.pl').`.
  Run with `swipl -q -f tests/test_q1.pl -g run_tests -t halt`.
- **Include every example from the handout**, plus edge cases: empty input,
  smallest input, no-solution cases, division by zero (P2), `n = 0`, depth 100 and
  10,000 elements (S2).
- **Run the Racket tests** from `78/` in Git Bash, the way the grader runs the files:
  ```
  cat code/78_q4.rkt tests/test_q4.rkt > ../run_q4.rkt && racket ../run_q4.rkt > ../out_q4.txt
  grep '^; expect: ' tests/test_q4.rkt | sed 's/^; expect: //' | diff - ../out_q4.txt && echo PASS
  ```
  **Delete `run_*.rkt` and `out_*.txt` afterwards.** They land in the repo root
  and must never be committed.
- **Before every commit:**
  1. `racket code/78_q4.rkt` or `swipl -q -f code/78_q1.pl -t halt` prints nothing.
  2. All tests for your problem pass, including earlier units.
  3. Scheme only: the whitelist grep from `scheme-dev/SKILL.md` matches only
     words inside comments.
  4. Run the exact grader commands from `CLAUDE.md` once.

## 11. Talking to the AI

- **Claude Code in this repo:** it loads `CLAUDE.md` automatically. At the start

- **ChatGPT or another AI for coding:** paste `CLAUDE.md`, this guide and the
  skill file in first, every new chat.
- **Watch for** the AI touching other files, committing, adding attribution,
  using banned built-ins or libraries, or doing more than one unit. Reject that
  output and re-prompt.
- **Never paste** your password, GitHub tokens or personal details into an AI.

### Using ChatGPT (or any AI that can't see the repo or run code)

Without Claude Code, the AI can't read your files, run Racket or Prolog, or
check a diff, so those jobs are yours. Follow these steps every time:

1. **Start every new chat with context.** Paste, in this order: `CLAUDE.md`,
   `TEAM_GUIDE.md`, then the skill file for your language. Tell it: "Follow
   these rules for every answer in this chat."
2. **Paste the current code file** you're working on (the latest version after
   `git pull`), so the AI builds on the real code and not on a guess.
3. **Send one unit prompt** (Section 5). Add this line to it: "Give me only the
   new definitions to append, not the whole file."
4. **Apply the change by hand.**
   - Add only the new lines, **below** the existing code, under a section
     header comment.
   - **Never paste a whole file over the existing one.** The AI may have quietly
     changed or dropped someone's code.
   - Don't let it "tidy up" existing functions. If its answer changes existing
     lines, reject that part.
5. **Run every check yourself.** The AI's claim that "tests pass" means nothing,
   because it couldn't run them.
   - Loading prints nothing: `racket code/78_q4.rkt` or
     `swipl -q -f code/78_q1.pl -t halt`
   - The unit's examples give the expected output. Run them with the test
     method in Section 8, or with a temporary run file you delete afterwards.
   - All earlier tests for your problem still pass.
   - Scheme: run the whitelist grep from `scheme-dev/SKILL.md` and read every hit.
   - Prolog: no warnings on load, and no `assert`, `clpfd` or other banned
     predicates or libraries.
6. **If something fails,** paste the exact error or output back to ChatGPT as a
   new prompt (for example `S2.b1 fix`). **Log that prompt too.**
7. **Check the diff:** `git diff` should show only your new lines in your file.
   If anything else changed (other functions, whitespace, every line, other
   files), undo it before committing.
8. **Log and commit** as usual (Sections 6 and 7): `sent by: <you>`, and for a
   prompt ChatGPT both drafted and answered, `drafted with: self` or
   `drafted with: ChatGPT`, whichever is true.
9. **Ask ChatGPT to explain every line** you're about to commit. You must be
   able to explain it yourself in the viva.
